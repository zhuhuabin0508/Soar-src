# 后端「假死」自愈与排查

> 现象关键词：容器 Up、端口能连、`/api/v1/*` 全部超时，前端整站转圈加载。

## 1. 症状

- `docker ps` 显示 `soar-backend-dev` 为 `Up`（甚至 `healthy` 之前的状态也正常）；
- 宿主机 `curl http://127.0.0.1:8001/api/v1/version` 无响应（超时，而非 4xx/5xx）；
- `docker exec -it soar-backend-dev sh` 可以正常进入，但 `docker logs` 里**没有**对应时刻的访问日志；
- 前端所有接口一直 pending，页面加载不出数据。

注意：本机若开了系统代理，PowerShell 的 `Invoke-WebRequest` / `curl` 会走代理导致「误判超时」，
探测请加 `--noproxy '*'`：

```powershell
curl.exe --noproxy '*' -s -o NUL -w "%{http_code} %{time_total}s`n" -m 5 http://127.0.0.1:8001/api/v1/health
```

## 2. 根因

后端以**单进程 uvicorn** 运行（已禁用 `--reload`），FastAPI 的 async 路径全部跑在
同一个事件循环里。只要有一个**同步阻塞**操作占住事件循环（未设超时的外部 HTTP 调用、
docker socket 调用、死锁、超长同步循环、线程池被占满等），进程不会崩，但会「假活」：
端口还在监听、容器还是 Up，可所有请求都排不上队 → 表现为全站转圈。

本次事故的直接诱因还包括**重载风暴**：`uvicorn --reload` 默认监听整个 `/app` 目录，
而 `/app/uploads`、`/app/backups` 是写入频繁的数据卷（备份/附件），每次写入都触发热重载，
叠加 `--timeout-graceful-shutdown` 默认 30s，旧进程关闭时容易卡在半死状态。

## 3. 三层防线（已内置，无需手工操作）

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 进程级看门狗 | `backend/app/core/loop_watchdog.py`，在 `backend/app/main.py` 的 lifespan 末尾启动 | 后台守护线程每 5s 向事件循环投递心跳协程；若默认 90s 内（约 18 次探测）心跳都没被执行，判定卡死 → `faulthandler` 打印**全线程栈** → `os._exit(1)` |
| 容器健康检查 | `docker-compose.yml` 的 `backend-dev.healthcheck` | 每 30s 请求 `GET /api/v1/health`（不查库、不走线程池的轻量端点），3 次失败（约 90s）→ 容器 `unhealthy`，`docker ps` 一眼可见；**仅标记状态，Docker 不会因 `unhealthy` 自动重启容器** |
| 自动拉起 | `docker-compose.yml` 的 `restart: unless-stopped` | 仅当容器**进程退出**（看门狗 `os._exit(1)`、崩溃、OOM 等）时由 Docker 数秒内重启；`unhealthy` 但进程仍在时不触发重启 |

> 结论：真正的「假死自愈」由进程级看门狗负责（杀进程 → restart 拉起）；
> healthcheck 只用于**观测/告警**。若 healthcheck 长时间 `unhealthy` 而容器未重启，
> 说明进程还活着但事件循环被阻塞，需人工 `docker restart` 或按第 5 节定位阻塞点。

配套的稳定性改动：

- `--reload` 已禁用（`docker-compose.yml` 的 `backend-dev` 直跑 uvicorn）：reloader 文件监听
  与重载风暴正是事故诱因，改后端代码后需 `docker restart soar-backend-dev` 或走 `deploy/deploy.sh`；
- `--timeout-graceful-shutdown 10`：退出/重启时最多等 10s，避免卡在优雅关闭；
- `PYTHONFAULTHANDLER=1`：卡死时能打印 C 层堆栈；
- **长耗时任务必须移出事件循环**：同步解析大文件/批量下发等同步 I/O 应以 `def` 端点
  （FastAPI 自动放入线程池）或 `run_in_threadpool` / `asyncio.to_thread` 执行，并设置
  文件体积/行数上限与外部调用超时。否则任务超过看门狗阈值会被误判卡死并强杀。

## 4. 可调参数

在 `.env.dev`（参考 `.env.example`）中配置，改完执行 `docker compose --env-file .env.dev up -d --no-deps backend-dev` 重建容器生效：

```ini
# 卡死判定阈值（秒）。默认 90：
#   调小恢复更快，但启动/大批量导出等长同步任务可能被误判；
#   调大更保守，恢复更慢。
LOOP_WATCHDOG_TIMEOUT=90
# 心跳探测间隔（秒），默认 5；代码内会限制不超过阈值的一半
LOOP_WATCHDOG_INTERVAL=5
# 总开关（默认 true）。确属预期的长时间同步任务可临时关闭
LOOP_WATCHDOG_ENABLED=true
```

## 5. 排查步骤

```powershell
# 1) 容器是否健康（healthy / unhealthy / starting）
docker inspect soar-backend-dev --format '{{.State.Status}} health={{.State.Health.Status}}'
docker ps --filter name=soar-backend-dev

# 2) 轻量健康端点（应返回 200，正常耗时 < 50ms）
curl.exe --noproxy '*' -s -m 5 http://127.0.0.1:8001/api/v1/health

# 3) 看门狗是否在跑（启动时必有一行）
docker logs soar-backend-dev 2>&1 | Select-String 'watchdog'

# 4) 是否发生过卡死/自动重启（看线程栈，直接定位阻塞行）
docker logs --tail 200 soar-backend-dev 2>&1 | Select-String '卡死|Thread 0x|File "'
```

若日志中出现：

```
[watchdog] 事件循环已卡死 91.3s（阈值 90.0s），打印线程栈后退出进程，由 Docker 自动重启
Thread 0x00007f... (most recent call first):
  File "/app/app/xxx.py", line N in some_func
```

说明自愈已生效（服务会自动恢复），同时**栈顶那一帧就是阻塞点**——请把它改为线程池执行
（`fastapi.concurrency.run_in_threadpool` / `asyncio.to_thread`）或为外部调用显式设置超时，
这才是根治。看门狗只保证「不长时间假死」，不替代对阻塞点的修复。

## 6. 手工恢复（自愈未触发时）

```powershell
docker restart soar-backend-dev      # 或 bash dev.sh restart b
```

重启后 `docker logs` 会重新出现 `[watchdog] 事件循环看门狗已启动` 与
`Application startup complete.`。**切勿** `docker compose down -v`（会清空数据卷）。
