# 工单设备动作修复说明

本文是唯一实施依据。基线 `7da45b0`（`main`）。

这次只改下面「要改」的四项。它们会直接造成错误下发、工单提交被拦住，或保存模板时丢掉配置。后面「先不改」的项以后再做，这次不要实现。

不要改 `README.md`、`docker-compose.yml`，不要改无关文件。不要 `git commit` / `git push`，除非另行要求。遵守 `rules/CONSTITUTION.md`、`rules/STYLE.md`。不要引入 Alembic，这次也不要加表。

后端测试加在 `backend/tests/test_ticket_device_action.py`。用假设备执行器看调用次数。不要为验证去打真实设备。

## 这次要改

### 1. 只读封禁原因由服务端定稿

流转现在只在提交值为空、或等于 schema 默认值时才套模板。`initialDeviceParams` 会用同名历史字段盖掉模板。字段 key 为 `reason` 时，只读框不是工单号，直接调接口也能换原因。

内置规则只认参数名 `reason`。查询、解封动作也会变成只读工单号。

`normParamConfig` 会删掉「可编辑且没有模板」。后端又把「没有 reason 配置」当成内置只读，用户保存的可编辑会丢。

改这些位置：

- `backend/app/core/ticket_device_action.py`
- `backend/app/api/v1/tickets.py` 里 `advance_ticket` 组参数的那段（约 2186–2207 行）
- `frontend/src/pages/TicketDetail.jsx` 的 `initialDeviceParams`
- `frontend/src/pages/TicketFlowEdit.jsx` 的 `normParamConfig`（约 158–168 行）

做法：

1. 在 `ticket_device_action.py` 做一个定稿函数。`advance_ticket` 用它，不要在路由里散落判断。
2. `readonly` 和 `hidden` 忽略客户端传来的值。有 `default_template` 就按工单上下文解析，否则用 schema 默认值。仍为空且必填，就返回错误，带上动作和参数名。
3. `editable` 且请求标明该参数被处理人改过（`device_runs[].overridden_params`）时，用用户输入。没改过则用模板，再否则用 schema 默认值。没有模板的普通参数，仍用客户端提交的非空值。
4. 本次提交的字段按「键是否出现」盖住历史值。`""`、`0`、`False` 都算出现。不要用 `x or ""` 判断有没有填。
5. `initialDeviceParams` 禁止用历史字段的同名 key 填设备参数。字段值只通过模板 `{f:字段key}` 或旧的 `params` 映射进入设备参数。
6. 内置封禁原因三条同时满足才生效：`action_type == block_ip`、参数名是 `reason`、没有显式 `param_config.reason`。模板是 `工单同步：{ticket_no}`，展示只读。其他动作类型的 `reason` 不接管。
7. `normParamConfig` 保留 `{display: "editable"}`，即使没有模板。只有用户清除覆盖才删掉这个键。打开配置面板但没改，不要把所有参数写成显式可编辑。
8. `sync_block_ip_record` 的台账原因用定稿后的 `params["reason"]`。没有这个参数时再写 `工单同步：{ticket_no}`。去重键这次不动。

测试：

- 历史字段 key 为 `reason` 时，封禁动作下发的仍是 `工单同步：{工单号}`。请求体另传 reason 也改不掉。
- reason 设为可编辑且不填模板，保存、重开、发布后仍可编辑。清除覆盖后恢复内置只读。
- 解封或查询动作的 `reason` 保持可编辑。
- 可编辑参数被手改后，其他字段变化不覆盖它。
- 本次值为 `0`、`False` 或 `""` 时，不用历史值，也不被模板盖掉。
- 台账 `reason` 与下发给设备的 reason 一致。

### 2. 模板按本次填写重算

详情解析模板只用历史记录。隐藏且必填的 `{f:src_ip}` 要等当前节点才填写时，前端发现参数为空，请求发不出去。页面上已经有旧值时，服务端把旧值当成用户输入，不再重算。

做法：

1. 定稿时的字段上下文包含历史记录和本次 `field_values`。
2. 前端预览保留 `default_template`，用历史记录加当前表单现算。用户改别的参数时，不要把当时的模板结果冻进 `actionParams`。
3. 带 `default_template` 的隐藏参数，提交前不要因为空值拦截。可编辑参数仍做本地校验。最终仍为空由服务端拒绝，这次还不会调用设备的保证见第 3 项。

测试：

- 隐藏 `ip={f:src_ip}`，本节点填写或改掉 `src_ip` 后，下发的是新 IP，工单可以提交。
- 单个动作的必填模板最终为空时，这个动作的设备调用次数为 0，错误能指出参数名。

### 3. 全部参数校验通过之前，不调用设备

`advance_ticket` 现在边校验边调用。动作 A 已经打到设备上，动作 B 参数不合法时，A 无法撤销。

这次只改顺序，不加表，也不要在循环里 `db.commit()`。

本次每个要执行的动作，先做完定稿、设备与动作是否可用、`prepare_device_params`。任一失败就返回全部错误，一次设备都不调用。设备在调用过程中失败、超时、重试，这次不处理。

测试：

- 动作 A 参数合法，动作 B 参数非法：调用总次数为 0，工单仍在原节点。
- 动作 A 参数合法，动作 B 的必填模板解析为空：调用总次数为 0。

### 4. 保存模板时不要弄丢旧配置，也不要清不掉 ban_sync

`_strip_legacy_ban_sync` 遍历的是模板 JSON 的顶层值，碰不到 `nodes` 数组里的节点。编辑器 `buildPayloadNodes` 展开对象时会把 `ban_sync` 带回去。

`normNodeRoutes` 重组动作时丢掉 `id`、`when`、`params`。`TicketFlowEdit.jsx` 约 1084 行仍要求节点级动作有 `id`，所以旧的节点级动作打开后再发布会被拦住。`ticket_flow.py` 并不要求动作带 `id`，这次不要给后端加这条校验。

`POST /tickets/{id}/device-actions/execute` 只按 `id` 和 `when` 判断。没有 `when` 就当命中。新动作一旦补上 `id`，判断字段未命中也能从这里下发。这个接口目前也不走 `prepare_device_params`。

做法：

1. `_strip_legacy_ban_sync` 遍历 `payload["nodes"]`，对节点去掉 `ban_sync`，写回 `flow.nodes`。
2. `buildPayloadNodes` 不要把 `ban_sync` 带回去。
3. 不要改已经创建的工单快照。在途工单继续按快照里的旧同步执行。保存模板只影响重新发布之后的新工单。
4. `normNodeRoutes` 保留 `id`、`when`、`params`。还不能放进字段卡的旧动作留在节点级。
5. 新绑定的动作在编辑器里创建时就生成稳定 `id`。已有 `id` 不重造。前端校验和提交使用同一份已经带 `id` 的数据。不要只在 `buildPayloadNodes` 里补 `id`。
6. 旧执行接口：配置带 `judge_field` 时返回 400，这类动作只在提交流转里执行。没有 `judge_field` 的旧动作仍按 `when` 手动执行，没有判断字段不等于不执行。调用设备前走 `prepare_device_params`。这次不为这个接口加执行记录，也不补台账。

测试：

- 带 `ban_sync` 的模板保存后该键消失。重新发布后，新工单快照里没有它。保存前已经创建的工单快照不变。
- 带 `id / when / params` 的旧动作打开、保存、再打开，这三项都在。`when` 不满足时旧接口拒绝，设备调用次数为 0。
- 新绑定的动作在发布前已经有 `id`，再保存一次 `id` 不变。
- 带 `judge_field` 的动作即使有 `id`，直接请求旧接口也不调用设备。

## 这次先不改

下面这些以后再做。这次不要建表、不要加唯一索引、不要改 `execute_device_action` 的重试，也不要加恢复接口。

- 多个动作里，前一个设备已经调用成功、后一个设备调用失败时，平台记录被回滚，重试会再次下发。要靠执行记录和短事务，不是这次能顺手改完的。
- 执行器在 `max_retries > 0` 时对异常和 HTTP 5xx 的自动重试。
- `pending / running / unknown` 与回退、转办、取消的互斥，以及结果不明后的人工确认接口。
- 封禁台账只按 `(ticket_id, ticket_node)` 留第一条。同节点第二个 IP、旧 `ban_sync` 和新动作抢同一条记录，留到有执行记录之后再改去重键。
- 不批量改历史 `flow_snapshot`。
- 不改工单监控大屏和封禁状态查询。
- 不改 `hermes/executor.py`。

交工时写清：改了哪些文件、跑了哪些测试、上面「先不改」的哪条还没成立。不要把「参数校验已经提前」写成「设备中途失败也不会重复下发」。
