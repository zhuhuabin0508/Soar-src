## 2. 遗留问题明细

### 问题 1 🔴 High：封禁双轨 + 状态三真相源 —— ✅ 已修复（2026-10-20）

**修复方式**（采用"方案 B 退役 + 防御纵深"）：

- `definitions/legacy.py`：`block_ip_on_firewall` 加入 `REMOVED_BUILTIN_TOOLS` → 种子目录过滤 + 启动时 `_cleanup_removed_and_legacy` **删除存量 DB 行**；
- `core/tool_templates.py`：用户侧模板同步移除；
- `agent/hermes/tool_search.py`：`_JUDGMENT_CORE_TOOL_NAMES` 移除；
- `devices/firewall.py`：Mock **中性化**——残留调用返回 `error` 而非假成功（防御纵深）；
- `definitions/builtin.py`：`record_ban` 描述改指向 `block_ip`；
- 测试 `test_tool_permission_gate.py` 改为断言"非可调用预设"，**8 passed**。

**复审核验**：`_cleanup_removed_and_legacy`（seed_service.py:25-40）会 `db.delete` 存量行，已有数据库重启即清理，无需手写迁移。✅

**修复后残留（并入问题 4/5 清理）**：`tool_result_classification.py:23` 与 `verification.py:44` 名单中该名再次成为死名（无害，工具已不可装配）；`tool_runner.py:744-747` 沙箱注入成为死代码。

<details><summary>原始问题描述（存档）</summary>

**现象**：旧 DB 工具 `block_ip_on_firewall`（seed `enabled:True`）经 tool_runner 沙箱直调**内存 Mock**（`firewall.py` 的 `_blocked_ips` set）；而语义工具 `block_ip` 走 DeviceGateway → 真实设备。封禁状态分散在**三处**：

1. Mock 内存 set（`block_ip_on_firewall` / `is_ip_blocked`）
2. BannedIP 表（`record_ban` 写入 / `query_banned_ip` 查询）
3. 真实设备状态（DeviceGateway → action_executor → HTTP）

**后果**：生产环境 LLM 若选中旧工具，拿到**假封禁成功**（仅内存态），且无 DeviceCallLog、无幂等键；多 worker 部署下内存态互相不可见，幂等彻底失效。

**位置**：

- `backend/app/core/tools/definitions/builtin.py:217-242`（seed 定义，`enabled: True`）
- `backend/app/core/tool_runner.py:744-747`（沙箱命名空间注入 Mock 函数）
- `backend/app/devices/firewall.py:12-50`（Mock 实现，docstring 自述"适用于开发调试与单实例场景"）
- 对照：`backend/app/devices/as_tool.py:434-465`（语义 block_ip 正确走 Gateway）

**修复建议**（二选一）：

- 方案 A（推荐）：旧工具 coroutine 改为复用 `resolve_default_block_device` + `DeviceGateway.invoke`，与语义工具同链；
- 方案 B：seed 降级为 `enabled: False`，仅开发环境手工启用；`tool_search.py:204` 的 `_JUDGMENT_CORE_TOOL_NAMES` 同步移除。

**违反约束**：「所有设备动作调用必须经 DeviceGateway 收敛，不得绕过直接调用底层执行器」。

</details>

### 问题 2 🔴 High：管理 API 直调 Mock 绕过 DeviceGateway —— ✅ 已修复（2026-10-20）

**修复方式**：

- `api/v1/tools.py` `POST /block_ip` 改为：`resolve_default_block_device`（显式 `device_id` 校验设备可用性）→ `DeviceGateway.invoke(source="api")`，带幂等键、`user_id`、错误→400；
- 权限从 `require_role("admin","analyst")` 升级为 `require_permission("device","edit")`（与全站权限体系一致，粒度更细）。

**复审核验**：`DeviceGateway.invoke` 签名支持 `source="api"` 与 `user_id` ✅；前端无 `/tools/block_ip` 调用方，`device_id` 新必填字段无实际破坏 ✅。

**修复后残留（并入问题 5 清理）**：`dependencies.py:47-70` 的 `FirewallDevice`/`get_firewall_device` 成为死代码（连带 `firewall.py` 的 `is_ip_blocked`）。

**备忘**：API 幂等键不含 `user_id`——不同管理员对同 IP+参数+设备的重复请求会命中幂等（对封禁语义合理，仅登记）。

<details><summary>原始问题描述（存档）</summary>

**现象**：`POST /api/v1/tools/block_ip` 直接调用 `firewall.block_ip_on_firewall`（内存 Mock），不经 DeviceGateway——无幂等键、无 DeviceCallLog、无证据链。`FirewallDevice` DI 封装（`dependencies.py:47-70`）是遗留的装配根，与工具契约体系平行存在。

**位置**：

- `backend/app/api/v1/tools.py:74-100`（端点实现）
- `backend/app/dependencies.py:47-70`（FirewallDevice 单例 DI）

**修复建议**：改走 `DeviceGateway.invoke(source="api")`；`FirewallDevice` 封装随之退役。若该端点定位是"运维直调"，也应有调用日志与幂等保护。

**违反约束**：同问题 1（设备统一执行缝）。
