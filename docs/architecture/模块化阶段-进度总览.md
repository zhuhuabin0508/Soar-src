## 一、一句话现状

> **本阶段「代码需求」已完成闭环（约 95%）；不算「全部交付上线」。**  
> 模块化 + 设备接入 + §十三 危险治理（阶段 0~6d）代码已齐；工作区相对 `main` 的开发项已落在分支 `feat/modular-decoupling`。
>
> **本阶段「模块化」落地的是什么（2026-10-19 核实）**：
> - ✅ **对外工具契约解耦**（主成果）：`ToolDescriptor` + `ToolRegistryBuilder` + 治理名单派生；双入口 `invoke_agent` / `invoke_tool`；设备经 Gateway / 投影 / 门面 / 语义 `block_ip` 向上暴露。
> - ◐ **物理目录只局部变清晰**（`platform/`、`devices/`、`core/tools/`），**不是**整仓按业务域拆包重构。资产 / KB / 通知等仍多在 `core/` + 扁平 `api/v1/*`；模块间横向 import **未清零**（例：`devices/as_tool.py` → `app.agent.tool_builders`）。
> - 权威界定见 [`模块化阶段-背景与目标.md`](./模块化阶段-背景与目标.md) §3：「模块化 ≠ 拆成 N 个独立服务」。
>
> **工具危险能力怎么控（现行，2026-10-20）**：
> - **谁能看见工具**：Agent 白名单先圈范围，再按当前用户角色裁掉无权工具。`critical` 不进入对话列表。
> - **Agent 对话**：`low` / `medium` 直接执行；`high` 在当前对话框确认后，签发 15 分钟一次性凭证，执行前由进程内网关重读契约并核销；`critical` 直接拒绝。
> - **工作流**（不传登录用户）：直接执行，不要求凭证，也不拦截 `critical`，仍写审计。
> - **工作台审批中心**：仍只服务工作流封禁等既有能力；**不**处理 Agent 高危工具。
>
> **路线（2026-10-20 更新）**：
> 1. **本阶段收尾**：Agent **统一对话**代码已落地，待体验验收。入口只挂查询工具，不挂设备写。
> 2. **下一阶段**：以 **资产组模块** 为试点做**物理模块拆分**。
> 3. **上线配套（并行/穿插）**：§九 界面测 + §9.3 配置盘点 + 部署。
>
> 详细计划见 **§十四**。

## 十一、语义 `block_ip` 的两个设计点（2026-10-19 已决 → 见 §十三）

> **本文保留为决策过程记录**；最终结论见 **§十三**：§11.1 → 装配 **A2**；§11.2 → **Agent 确认 / 工作流直通**；O1 → **唯一即用（tags 仅多台消歧）**。

> **背景**：P2-4（语义 `block_ip`）开工前有**两个设计点需讨论拍板**，暂不实现。此处登记**完整方案**，定了再动手。
> **排期（2026-10-16）**：本节 3 个待决点（§11.1 装配标准 / §11.2 确认前置 / O1 tags 口径）计划 **下周集中讨论拍板**；拍板后即可解锁 P2-4b / P2-4c。

### 11.1 装配标准：哪些 Agent 的工具栏里出现 `block_ip`

**核心原则（已确认）**：工具在不在 = **有没有封禁能力**。绝不能无条件发给所有 Agent，否则：
① 研判 Agent 拿到写工具（违反「研判与执行分离」）；
② 误封入口变多（证据链只挡「没查证据就封」，挡不住「查了证据但判断错」）；
③ 工具与能力脱钩（没设备的 Agent 也看到，一调就报错，白费轮次）。

| 选项 | 规则 | 效果 | 评价 |
|---|---|---|---|
| **A1 粗** | `enabled_devices` 非空 → 有 `block_ip` | 勾了台「只能查日志」的设备也会看到 `block_ip`（一调就报错） | 简单 |
| **A2 细（建议）** | `enabled_devices` 范围内存在「**启用 + 在线 + 有启用 `block_ip` 动作**」的设备 → 才有 | **能封才给**——工具出现即代表真的能封 | ✅ 与「工具 = 能力」完全一致 |

**授权方式**：管理员只配 `enabled_devices`（这个 Agent 能用哪些设备），`block_ip` 由系统**派生**——**不是硬编码名单，也无需人工逐个把 `block_ip` 勾进 `enabled_tools`**。

> 举例：「处置 Agent」勾了防火墙 3（有 block_ip 动作）→ 自动获得 `block_ip`；「研判 Agent」不勾任何设备 → 连 `block_ip` 的影子都看不到。

**待确认**：A1 / A2 选哪个（**建议 A2**）。**待讨论方**：产品 / 项目组。

### 11.2 人工确认前置：`block_ip` 执行前是否要人工确认

**现有机制（平台已有两档）**：

| 档位 | 机制 | 现状 | 强度 |
|---|---|---|---|
| **软确认** | verification 返回 `needs_clarification` → 强制 LLM 先调 `clarify` 问用户 | ✅ 已有（[`verification.py:191`](../../backend/app/agent/hermes/verification.py#L191)，带「确认封禁 / 取消」选项） | 必须先问，但问完可再调执行 |
| **硬确认** | `trigger_workflow_skill` 触发带 `human_review` / `approval_ticket` 节点的工作流 → Agent turn **中断**（`Execution.status=waiting_for_approval`），等审批中心人工通过才继续 | ✅ 已有且完整（[`skill_engine.py`](../../backend/app/agent/hermes/skill_engine.py) + `/approvals` API + Redis 信号 + 超时默认驳回） | **真暂停**，人不点不执行 |

**架构取向**：人工确认本就在**工作流路径**——§6.4「生产封禁主路径的写操作默认由工作流节点完成」→ 「研判 → 工作流（含 `human_review`）→ 执行」天然带硬确认，**不用额外做**。

**对话直调 `block_ip` 要不要硬确认？** 目前**没有**（§6.8 定义为「Gateway 薄封装」直调）。两条方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 复用现成（建议）** | 让对话封禁也走那条带 `human_review` 的工作流（而非直调 Gateway） | 零新机制、与路径 A 统一；代价是对话封禁变异步、要等审批 |
| **② 新做门控** | 给 Agent 工具加「执行前暂停 + 前端弹窗确认」 | 需前端确认 UI + Agent 暂停/恢复状态机，属**新功能** |

**待确认**：对话封禁要不要硬确认；要的话选 ① 还是 ②（**建议 ①**）。**待讨论方**：产品 / 安全运营。

### 11.3 对 P2-4 的影响（施工边界）

| 设计点 | 影响 |
|---|---|
| 11.1 定了 | 才能在 `_register_device_tools` 里写对「是否装配 `block_ip`」的判断 |
| 11.2 定了 | 才决定 `block_ip` 是「直调 Gateway」（现方案）还是「触发工作流」 |
| **不受影响、可先做** | `resolve_default_block_device`（默认设备解析三步：`default_device_id` → tags 兜底 → 报错不静默）——**与上述两点解耦**，可先落地 |

> **结论**：P2-4a 可**先做「默认设备解析 + `block_ip` 构建器」**，只把「**装配条件**」与「**确认前置**」两个挂钩点**留空待定**。

### 13.4 确认策略（`app/core/tools/policy.py`）

```python
SCENARIO_AGENT, SCENARIO_WORKFLOW = "agent", "workflow"

_CONFIRM_REQUIRED = {"critical": {"agent"}, "high": {"agent"},
                     "medium": set(), "low": set()}

def requires_confirmation(danger_level: str, scenario: str) -> bool:
    return scenario in _CONFIRM_REQUIRED.get(danger_level, set())
```

| 危险层级 | **Agent** | **工作流** |
|---|---|---|
| critical / high | **人工确认** | 直接 |
| medium / low | 直接 | 直接 |

工作流入口不传登录用户：不要求凭证，不拦截 critical，仍写审计
