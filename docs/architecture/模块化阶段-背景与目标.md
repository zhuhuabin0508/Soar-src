## 1. 项目是什么

**SOAR**（Security Orchestration, Automation and Response）安全运营自动化平台。

一句话定位：

> **以 LLM 为底座，各业务模块以「工具」形式向 Agent 暴露能力，由 LLM 根据上下文串联调用；模块实现内聚，模块之间不直接耦合。**

### 技术栈

| 层 | 技术 |
|---|---|
| 后端 `backend/` | Python + FastAPI + Celery + PostgreSQL + Redis + SQLAlchemy |
| 前端 `frontend/` | React + Vite |
| Agent 运行时 | 自研 **Hermes ReAct 引擎**（`backend/app/agent/hermes/`） |
| 统一入口 | `invoke_agent` / `invoke_agent_sse`（`backend/app/platform/agent_runtime.py`） |

## 2. 当前架构（分层模型）

自下而上五层（L1 实现 → L5 交付），编排中枢 LLM 位于 L2 之上驱动下层，不占独立层编号：

```
  ┌─────────────────────────────────────────────────────────────┐
  │  编排中枢（LLM / Hermes ReAct）  — 驱动下层                   │
  └────────────────────────────┬────────────────────────────────┘
                               │
  ┌────────────────────────────▼────────────────────────────────┐
  │  L2  平台运行时                                              │
  │  invoke_agent · invoke_tool（规划）· tool_engine · 治理链    │
  └────────────────────────────┬────────────────────────────────┘
                               │ 仅通过工具契约向上暴露
         ┌─────────────────────┼─────────────────────┐
         ▼                     ▼                     ▼
    [设备模块]            [安全/资产/KB]         [工作流/通知]
         │                     │                     │
         └─────────────────────┼─────────────────────┘
                               ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  L1  模块实现（不对 LLM 暴露：executor / gateway / runner）   │
  └─────────────────────────────────────────────────────────────┘

  L3 注册层 — ToolCatalog → ToolRegistryBuilder
  L4 声明层 — Tool 表、DeviceAction、Agent ORM、Workflow JSON、Skill
  L5 交付层 — UI、模板、导入导出（只写 L4，执行必须经 L2）
```

**六条架构规则**（全文只此一套，必须遵守）：
1. **LLM 只通过工具认识世界**——不直接访问 DB、HTTP、厂商 API。
2. **模块只向上暴露工具契约**，模块间禁止横向 import 实现代码。
3. **工具串联由 LLM 中介**；固定 SOP 用工作流节点。
4. **三种消费入口、一套 L1 实现**：对话、工作流、管理 API 共用同一执行缝。
5. **技能只改 prompt，不产生动作**。
6. **研判与执行分离**：研判 Agent 只读；写操作由工作流节点或处置类工具完成。

## 3. 核心概念：模块 → 工具契约 → LLM 编排

SOAR 的「模块化」不是把代码拆成 N 个独立服务，而是：

| 概念 | 含义 |
|---|---|
| **模块** | 安全研判、资产、知识库、设备、封禁、工作流等业务能力，实现内聚 |
| **工具契约** | 模块对外只暴露 `name + schema + execute + 元数据`，不 export SDK |
| **LLM 编排** | 工具 A 执行后结果交回 LLM，由 LLM 决定是否调工具 B（**禁止** Agent 层工具 A 直调工具 B） |
| **L1 复用** | 工具内部可以复用 `context_tools` 等函数，这是**允许**的 |

**关键结论（本阶段要达成的）**：加一个工具/模块 = 注册一个工具描述符，**不改引擎、不改治理链**。这就是「防止后续大范围返工」的根。

## 5. 本阶段最终目标

### 一句话目标

> 让「**加一个工具只需改一处**」成立，并**堵住已敞口的越权写路径**。

### 成功标准（5 条，缺一不可）

1. `ToolRegistryBuilder`（唯一工具工厂）建成，工具装配面**只有一个权威来源**。
2. 全仓库硬编码分类名单（**9 处**，见执行单 §3）全部改为**从统一注册表派生**，不再各自维护。
3. `block_ip_on_firewall` 等真实写工具**纳入证据链验证**，且证据可绑定目标 IP。
4. 其他既有 Agent 的工具装配结果**逐字节不变**（回归无破坏）。
5. 阶段 1 **不新增数据库列**（`enabled_devices` 属 P2 另计）。

### 为什么「契约定稿」是本阶段的根

当前代码里，「工具」的元数据**分裂成两层、互不映射**，且治理名单**混淆了三套命名空间**（详见执行单 §2）。若不先定契约，后续每加一个模块就要在 9 处名单里各改一遍、还容易漏（`block_ip_on_firewall` 已经被漏了）。定好契约后，这些名单全部变成「从描述符派生」，新模块零治理成本。

## 7. 术语表

| 术语 | 定义 |
|---|---|
| Hermes | 自研 ReAct Agent 引擎，唯一运行时 |
| `invoke_agent` | Agent 统一入口（对话/研判/工作流） |
| `invoke_tool` | 工具统一入口（阶段 2 落地，工作流/API 直调工具共用治理链） |
| 工具契约 | `name + schema + execute + 元数据` |
| `ToolDescriptor` | 本阶段定稿的统一工具描述符（运行时元数据权威） |
| 动作投影 | 每个 DeviceAction → `device_{device_id}_{action_id}` 工具（阶段 2） |
| 语义工具 | `block_ip`，内部解析默认设备后走 Gateway |
| 门面工具 | `device_action`，显式 device + action 下发 |
| DeviceGateway | 设备唯一执行缝（阶段 2 落地） |
| `tool_source` | 持久层来源（builtin/framework/security/custom/device） |
| `source` | 运行时来源（统一后的治理依据） |
| barrier | 顺序执行屏障（写工具必须 barrier） |
