## 1. 整体进度

平台是 SOAR 安全运营：Hermes 智能体、工作流、知识库、工单、设备封禁。当前有两条并行成果，**没有合成一条可上线的线**。

| 线 | 在哪 | 完成度 | 一句话 |
|---|---|---|---|
| Agent 基座 | `main`，2026-10-08 冻结 | 代码完成，体验验收未完 | `invoke_agent` 单门面，LangGraph 已删 |
| 工单 / 安博通封禁 / 大屏 | `main`，2026-11-02 下午 | 代码已进 `main`，设备验收未做 | 封禁真下发安博通，大屏改成累计去重 IP |
| 模块化 + 设备网关 | **只在** `feat/modular-decoupling` | 分支内代码约 95%，未合并、未上线 | 工具契约、DeviceGateway、对话内确认 |
| 智能体 V2 体验（向导、工具包、知识库运营） | 方案稿 | 未开工 | [agent-v2-iteration-plan.md](./agent-v2-iteration-plan.md) |
| Skill 包（zip / 脚本） | 方案稿 | 明确暂不开发 | [skill-package-plan.md](./skill-package-plan.md) |

```text
main          基座冻结 ── 设备直连（安博通 / 动作执行器）── 工单大屏口径（11-02）
                 \
                  \  10-14 处分叉，此后互未合并
                   \
分支               工具契约 ── DeviceGateway ── 危险确认闸 ── 统一对话（待体验）
```

分支相对 `main` **多 72 个提交、少 42 个提交**。少的那 42 个就是 10 月 23 日之后 `main` 上的工单、封禁、大屏、资产导入和健康检查。不能把分支当成 `main` 的超集。

## 3. 未完成，按这个顺序做

原则：先验收已经在 `main` 上、下午还在改的封禁；再把模块化分支合进来，并且让安博通走网关。不合完之前，不要在 `main` 上重做一套 Gateway，也不要在分支上重做下午的大屏。

### P0 安博通与大屏验收（在 `main`，不改架构）

方案原文三条验收仍是空的，见 [安博通阻断器封禁联动改造方案](./安博通阻断器封禁联动改造方案.md) §9。代码已在，缺的是设备可达时的实测。

| 序 | 做什么 | 完成标准 |
|---|---|---|
| P0-1 | 配了 `ban_sync` 的工单流转 | 设备黑名单出现该 IP；调用日志 `source=ticket`；失败时工单仍流转，且没有生效中的 `BanRecord` |
| P0-2 | 工单详情查封禁 | 展示设备条目字段；未封禁有明确文案；设备停用时有引导，而不是空表 |
| P0-3 | 封禁工作台 | 黑名单按所选间隔刷新；手动封禁/解封与设备一致；设备断开时平台状态不变 |
| P0-4 | 大屏口径 | 面板「累计封禁 IP」= 下钻列表条数；同一 IP 解封后再封禁只计 1；已取消不计入。用 `backend/tests/verify_ban_stats_query.py` 对 SQL，再用一屏真实数据看一眼 |

P0 做完，这条产品线才算收口。通过前不要把方案文档里的回退说明当成「还没写代码」。

### P1 把 `feat/modular-decoupling` 合进当前 `main`

分支交接写于 2026-10-23，当时约定「这次修复不要 merge」，预适配已经落在 `3004a9e`。那次约束到此为止。现在的任务就是合并，但**不能快进合并**：`main` 又走了 42 个提交，封禁实现和网关规则是反的。

分支硬规则：设备动作必须经 `DeviceGateway.invoke`，工具执行必须经 `invoke_tool`。`main` 的 `anbotong.py`、工单封禁、工作台手动封禁、到期解封都直接打执行器。合进去若保留直连，网关、幂等和确认闸会被绕开。

| 序 | 做什么 | 完成标准 |
|---|---|---|
| P1-1 | 以分支为底，把 `main` 的 42 个提交合进来。先不要推生产 | 冲突清单至少覆盖 `action_executor.py`、`tickets.py`、`ban_workflow.py`、`devices/`、前端封禁页。合完工作区能启动 |
| P1-2 | 工单封禁、手动封禁、解封、到期解封、黑名单查询改走 Gateway。保留安博通的动作定位（名称 → action_type → method+path）和成功判定（封禁要 `code=1`，解封只看 HTTP） | 全仓库设备写路径不再绕过 `DeviceGateway.invoke` |
| P1-3 | 跑分支既有测试 + 安博通统计脚本 | 失败集合不多于分支基线：`delegation_c11`×1、`parser_engine`×3、`sangfor_strategy`×6。不把这 10 个既有失败算进本次 |
| P1-4 | 按分支部署手册执行 SQL，再部署后端 | `device_call_logs` 的幂等列、`agents.enabled_devices` 存在。顺序反了会 `UndefinedColumn` |
| P1-5 | 补分支 §9 里会改变线上行为的四项 | `computer_use` / `schedule_cron` 必须显式启用；`search_assets` 只认资产类型；子代理写工具被剥离；手动封禁走网关。逐个现网智能体盘点，避免升级后工具悄悄失效 |

合并时以分支的网关和治理为准，以 `main` 的工单、大屏、黑名单页面为准。`3004a9e` 里「超过 20 个读动作不投影」要留下，否则青藤这类大动作集会把工具列表撑满。
