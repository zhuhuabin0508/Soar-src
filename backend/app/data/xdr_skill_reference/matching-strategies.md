# 匹配策略

## 五级匹配策略

需求匹配接口时，按以下优先级从高到低尝试：

### 优先级 1：精确匹配

接口概述直接描述了该需求。例如需求"查询告警列表"，接口概述写着"分页查询安全告警列表"——这是最直接的匹配。

匹配时读取每个接口文档的"接口概述"段落，判断是否直接涵盖了需求的核心操作和对象。

### 优先级 2：使用场景匹配

需求出现在接口的"使用场景"列表中。接口文档中的"使用场景"段落列举了该接口适用的典型业务场景。

匹配时读取每个接口文档的"使用场景"段落，判断需求描述是否与某个场景条目一致。

### 优先级 2.5：业务逻辑匹配

需求的核心操作与接口文档"业务逻辑"段落描述的实际行为吻合。接口概述有时表述笼统，但业务逻辑段落详细描述了接口实际做了什么——包括核心处理流程、数据转换逻辑、默认行为和特殊规则。

例如需求"查询最近7天的告警"，接口概述只写"查询告警列表"，但业务逻辑段落明确说明"默认查询时间范围为最近7天"——这种匹配比使用场景更精确，因为直接反映了接口的实际行为。

匹配时读取每个接口文档的"业务逻辑"段落，判断需求描述是否与接口实际行为一致。特别关注默认行为和特殊规则，这些信息对判断需求是否可满足至关重要。

### 优先级 3：参数能力匹配

接口的请求参数支持需求中的过滤条件。例如需求"按源IP查询告警"，接口的请求参数中有 `srcIps` 字段——虽然概述没直接说"按IP查询"，但参数能力满足需求。

匹配时扫描请求参数表，判断是否有参数能表达需求中的过滤条件。

### 优先级 4：关联接口推理

通过接口文档的"关联接口"字段发现可配合的接口。当一个接口不能单独满足需求时，查看其"接口定位 > 关联接口"字段，可能发现可组合的其他接口。

例如需求"查询告警后批量处置"，先匹配到查询接口，然后从其关联接口字段发现处置接口。

## 接口选型优先级（按"需求产出形状"选接口）

当需求可以匹配到多个候选接口时（如既能用 list 接口也能用聚合接口），按"需求产出形状"选择性能最优的接口：

| 需求产出形状 | 应选接口 | 不应选 | 原因 |
|---|---|---|---|
| 一个数（总数/满足条件的条数） | list 接口取 `total` | 聚合 `count(*)` | list 开销低于聚合，聚合不是为拿总数设计的 |
| 一组明细记录 | list 接口 | — | — |
| 按业务维度分组统计（Top N / 各分组计数） | 聚合接口 | — | — |
| 按枚举字段分布统计多个总数（如待处置/处置中/处置完成） | 聚合接口，`aggBy=该枚举字段`，`limit=枚举总数` | 为每个枚举值分别调 list | 一次聚合返回所有分组桶，性能远优于 N 次 list |
| 随时间分布的趋势 | 趋势接口 | list + 客户端聚合 | 趋势做时间分桶，客户端自己聚合开销大且有对齐风险 |

**性能排序**：list < 聚合 < 趋势。需求只需一个数时，永远用 list 取 `total`。

## 单接口 vs 多接口编排判断

**总原则：单接口优先——能用一个接口实现的需求，不要拆成多接口编排。**多个候选接口都能满足需求时，优先选单接口方案——多接口编排会引入额外的网络开销、数据一致性窗口、错误处理复杂度，能用单接口拿到结果就绝不拆。

### 单接口足够的条件

- 需求只涉及一个操作（纯查询或纯更新）
- 单个接口的返回数据已满足输出期望

### 需要多接口编排的条件

- 需求涉及"先查询后操作"（如查询告警 → 批量处置）
- 需求涉及跨业务域数据关联
- 单个接口返回数据不完整，需要补充查询
- 需要条件判断后走不同分支

### 跨业务域编排

需求涉及两个或以上业务域接口时（如告警 → 资产、事件 → 告警），按下述流程处理，**核心是每一步调用下一个接口前必须核对入参、保证第一次就调准确**——跨域接口之间没有 IDE 级别的类型检查，参数错位只会运行时才暴露，回退重调成本高。

#### 处理流程

1. **拆解需求为子任务**：把需求拆成"先后步骤"，每个子任务只涉及一个业务域。例如"查询最近 7 天高危告警涉及的内网资产并批量入库审批"拆为：
   - 步骤 A（告警域）：查最近 7 天高危告警，提取涉及的内网 IP
   - 步骤 B（资产域）：按内网 IP 查资产列表，提取资产 ID
   - 步骤 C（资产域）：对这些资产发起入库审批

2. **分域定位接口**：每个子任务只扫对应业务域子目录（如步骤 A 扫 `alerts/`、步骤 B/C 扫 `assets/`），不要全目录扫——这是子目录化结构的核心收益点。

3. **逐步核对入参再调用**：每写一步方案前，**必须完成 3 项核对**，确认完全对齐才输出该步调用方案：

   | 核对项 | 检查内容 | 失败处理 |
   |---|---|---|
   | ① 字段名映射 | 上一步返回值的字段名 → 下一步入参的字段名，名字不一致时显式写映射关系（如"步骤 A 返回 `entityIp` → 步骤 B 入参 `innerIp`"） | 字段名无法对齐时停下告知，不强行拼接 |
   | ② 类型/结构转换 | 上一步返回类型 → 下一步入参类型，string vs array、单值 vs 列表、JSON 字符串 vs 对象等差异要显式标注转换方式 | 需要包装/拆包时给出具体代码示例 |
   | ③ 枚举/单位差异 | 跨域枚举值是否同源（如告警 dealStatus 用 `AlertDealStatusEnum`，事件用 `IncidentDealStatusEnum` 或 TMG 枚举）；时间戳是否同单位（秒级 vs 毫秒级） | 枚举不一致时必须给出映射表；时间单位不一致必须显式 ×1000 或 ÷1000 |

4. **明确字段级数据传递**：方案中每个步骤都要标注：
   - 本步入参哪些字段来自前序步骤、哪些来自需求本身、哪些是常量
   - 本步返回值中哪些字段供后续步骤使用

#### 高频踩坑点（方案中必须显式提示）

- **批量大小限制**：上一步可能返回几千条数据，下一步批量接口可能限制单次 50/100 条——必须分批循环，方案里写明分批策略
- **空结果处理**：上一步返回 0 条时，后续步骤是否要跳过、是否要短路返回，方案里写明分支
- **过滤条件复用**：跨域时同语义过滤条件可能字段名不同（如告警的 `severity` vs 事件的 `severities`），不要假设可复用
- **分页一致性**：上一步跨页累计的数据，传给下一步时去重和排序如何处理

#### 红线：调用前不核对清楚就停

跨域编排中，任一步骤的入参出现以下情况必须停下告知用户，不强行写方案：
- 上一步返回值里找不到下一步需要的字段，且字段映射无法确认
- 跨域枚举值映射关系不明确，可能导致传错值
- 批量接口的批量上限未知，无法判断是否需要分批

### 无法匹配任何接口时

1. 先检查是否有需求理解偏差——回到需求澄清环节进一步追问
2. 确认需求理解无误但仍无匹配——明确告知"当前没有接口满足该需求"
3. 列出需求中哪些要素无法匹配到接口，逐项说明原因
